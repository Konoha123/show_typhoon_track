# M12 预存地点下拉缺陷归因与复现记录（2026-10-28）

> 背景：M11 验收后的使用验证中，用户报告「预存地点」原生下拉框异常：**拉开之后瞬间退出，
> 并选中拉开时鼠标指向的那个地点（未点击任何选项）**；其它下拉框未见异常，**稳定复现**，
> 真实浏览器 + 真实鼠标手动操作。本文档记录完整调查证据链、归因结论、Synergy 归因确认
> 方法（供执行回填）与可上报 Chromium 的报文素材；M12 的产品修复方案（内联选择器，
> 形态 II）见 `docs/里程碑基线.md`「M12」。

## 一、环境

| 项 | 值 |
|---|---|
| 浏览器 | Google Chrome 156.0.8078.47（stable，系统安装 /usr/bin/google-chrome） |
| 显示服务 | X11（Xorg，会话 :1；GNOME 桌面） |
| 屏幕 | 1920×1080 |
| 键鼠共享 | **Synergy 正在运行**（/opt/Synergy，进程实证） |
| 应用版本 | M11b（提交 7ac8280）；页面经 /static no-cache + `?v=` 引用，无旧缓存干扰 |
| 真实数据 | 用户 `places/places.csv` 187 行（约 180 个预存地点，8 洋区） |

## 二、现象与用户侧鉴别信息

1. 仅「预存地点」下拉（`#place-select`，当时为原生 `<select>`，182 个 option）异常；
   气旋/成员/起报等其它下拉未见异常；
2. 稳定复现（每次拉开均发生），偶发性排除；
3. 真实浏览器 + 真实鼠标手动单击，无自动化工具参与；
4. 下拉位于窗口中部（弹层向下展开，无屏幕边缘因素）；
5. 被提交的项「很像鼠标停留处」，因闪退过快无法目视确认。

## 三、调查证据链（按时间序，全部可复述）

### 3.1 应用代码排除（静态穷举）

- `#place-select` 选项的唯一重建链：`init → loadPlaces()（异步 /api/places）→
  renderBasinFilters() → fillPlaceSelect() → fillSelect(innerHTML='' 重建)`，
  触发点仅两个：页面 init、洋区复选框变化（弹层打开时不可能点复选框）；
- 全库（app.js）无 `focus()/blur()/dispatchEvent()/.click()`；无 focus/pointer 类监听
  （addEventListener 穷举仅 change/click/input/submit/resize 及 uPlot over click）；
- CSS `:has()` 仅影响 `.basin-check` 配色（无布局影响）；所有 select 共用同一规则；
- M11 两提交（ca77506/7ac8280）diff 未触及地点功能（逐行核对）；
- **复现窗口内 MutationObserver 实证：弹层打开期间零 option 变更**（见 3.4）。

### 3.2 CDP 合成事件不可达（headless + headed 各实验，共 3 组）

Playwright `page.click()` / `mouse.down+up` / 按住下移再抬起，无论 12 项短列表还是
182 项真实列表：`#place-select` 值始终不变、零 change 事件、X11 窗口树无弹层窗口——
**Chrome 156 的原生 select 弹层不响应 CDP 注入的鼠标事件**（合成事件打不开弹层），
因此任何 Playwright 用例从未触发过此缺陷（这也是 E2E 基线全绿的原因）。

### 3.3 X11 级真实注入（XTest，等价 xdotool 底层）：行为正常

经 ctypes 直调 libXtst（`XTestFakeMotionEvent/XTestFakeButtonEvent`，`XSynchronize` 模式；
XFlush 会触发段错误已规避，`XDefaultRootWindow` 符号在 ctypes 下崩溃已用 xwininfo
解析替代），在 **headed 用户同版本 Chrome** 上以坐标校准后的 X 级合成鼠标事件单击
`#place-select`：
- 事件序列：mousedown（trusted，命中 select）→ focus 触发 → **mouseup 被原生弹层
  消耗（document 层无 mouseup/click）** → 弹层保持打开、值不变——**完全正常**；
- 12 项与 182 项列表行为一致；
- 结论：**XTest 管道注入的「真实 X 事件」不触发缺陷**。

### 3.4 干净配置 + 用户真实鼠标：复现（决定性实验）

新开 Chrome 156（channel="chrome"，临时 user-data-dir，**无任何扩展与用户配置**），
页面挂载用户真实 places.csv（187 行），注入事件探针（select 的 change/focus/blur +
document 捕获阶段 mousedown/mouseup/click 坐标与 target + option 子树 MutationObserver），
**请用户以平时的真实鼠标操作**，60 秒窗口捕获（时间戳为页面 performance.now ms）：

```
[18s] mousedown(162,410)→#place-select  focus 触发
      mouseup(162,410)→#place-select   ← mouseup 回到了页面！
      click (162,410)→#place-select
[35s] mousedown(98,405)→#place-select  focus 触发
      mouseup(98,405)→#place-select    ← 同样回到页面
[53–57s] 用户点洋区复选框（LABEL/INPUT），期间才出现 MUTATION-options
最终：value=''、全程零 change、弹层打开期间零 DOM 变更
```

**解读**：原生弹层若正常打开并保持，会持有指针抓取——mouseup 根本不会到达页面
（3.3 的 XTest 实验正是如此）。而用户真实鼠标按下后 **mouseup 与 click 都回到了页面**，
即弹层在按下与抬起之间瞬间死亡。本窗口未见「选中某地点」，只因鼠标恰好悬停在弹层
第 0 行（占位符「— 选择预存地点 —」）上——提交占位符 = value=''，不触发 change；
用户日常遇到的「选中鼠标指向的地点」= 同一机制下光标落在真实地点行。

## 四、归因结论

缺陷不在本仓库代码。归因为：**Chrome 156 原生 `<select>` 弹层在「本机真实输入管道」
注入的事件流下，被立即驳回（dismiss）并提交当前高亮项（= 鼠标所指项）**。本机真实输入
由 Synergy（键鼠共享）注入（进程实证），其事件序列/状态与 XTest 合成事件存在差异，
且与弹层的活动指针抓取（XGrabPointer 语义）交互异常；「之前没有过」与 Chrome 近期
自动升级到 156 的时间点吻合（Chromium select 弹层输入处理回归的可能性大）。
最终确认依赖第五节实验。

## 五、Synergy 归因确认（供执行，结论回填本节）

1. 退出/暂停 Synergy（右键托盘图标 → Settings → 停止服务，或 `System → Stop`）；
2. 用**本机直连**输入设备（笔记本触控板 / 直插 USB 鼠标，不经 Synergy）打开工作台；
3. 反复点开「预存地点」及其它原生下拉各 3 次：
   - 若恢复正常（弹层稳定停留、点击选项才选中）→ 归因落定 Synergy×Chrome156 组合，
     可按第六节素材上报（Chromium 与 Synergy 双向）；
   - 若仍异常 → 归因修正为「GNOME/Xorg 本机输入×Chrome156」，同样按第六节上报；
4. 回填格式：「2026-10-__ 执行，Synergy __（停/未停），现象 __（复现/消失），执行人 __」。

## 六、Chromium 上报素材（英文草稿，可直接提交 issues.chromium.org）

```
Title: <select> dropdown popup dismisses instantly and commits the
hover-highlighted option on Linux/X11 with specific real-mouse input paths

Version: Google Chrome 156.0.8078.47 (Official Build) (64-bit)
OS: Linux/X11, GNOME, Xorg display :1, screen 1920x1080
Keyboard/mouse sharing software running: Synergy (input injected by Synergy)

Steps to reproduce (100% on affected machine):
1. Open any page with a <select> that has a long option list
   (reproduced with 182 options; also reproduces the popup flash with 12 options
   depending on cursor row). Example page served from localhost.
2. Single-click the <select> with the real mouse (events delivered through
   Synergy). Do NOT click any option.

Expected: dropdown popup opens and stays open until user clicks an option or
elsewhere; selection unchanged.

Actual: popup flashes open and dismisses instantly; the option under the
cursor at open time gets committed (change event fires with that option).

Evidence that this is input-path dependent (same machine, same Chrome build):
- Injecting trusted X-level events via XTEST (XTestFakeMotionEvent /
  XTestFakeButtonEvent): popup opens normally, holds the pointer grab
  (mouseup is consumed by the popup), nothing is committed. Normal behavior.
- With the user's real mouse (Synergy path), instrumented page listeners
  capture: mousedown on select -> focus -> mouseup AND click BOTH land back
  on the page element (i.e. the native popup died between press and release
  and released the grab). Zero DOM mutations on the <select> during this
  window (MutationObserver), so nothing in page JS dismissed it.
- Reproduces on a clean profile with no extensions.

Notes: - DevTools/CDP-injected mouse events never open the native select
popup in this build (value unchanged, no popup window in xwininfo), so
Playwright/Puppeteer tests cannot trigger this. - Suspected regression in
select popup input handling (active pointer grab) around Chrome 156;
did not reproduce before the recent auto-update.
```

## 七、与 M12 修复方案的关系

M12 将「预存地点」选择器重构为**内联常驻选择器（形态 II：搜索框 + 洋区筹码 + 常驻
列表）**，页面上不再存在任何原生 `<select>` 弹层交互——对弹层类缺陷（含本缺陷及
未来同类回归）**结构性免疫**；同时以搜索能力替代 182 项原生下拉的可用性瓶颈。
其余短列表下拉暂留原生（M12 决策 Q5），若后续在其它下拉出现同象，再按本记录方法
鉴别并扩展转换。

## 八、调查过程遗留事项

1. ctypes 直调 libX11/libXtst 的两个坑（规避方法见 3.3，留档复用）：
   `XFlush` 在 `XSynchronize` 模式下段错误（省略 flush 即可，同步模式逐调用送达）；
   `XDefaultRootWindow` 符号经 ctypes 调用崩溃（用 `xwininfo -root` 解析窗口 id 替代）；
2. 调查中多次进程崩溃遗留过孤儿 Chrome 窗口，曾污染一次坐标命中判断——后续做屏幕级
   实验前应先清理（`pkill -f "user-data-dir=/tmp/playwright"` 类）。
